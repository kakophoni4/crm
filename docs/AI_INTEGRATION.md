# Интеграция ИИ в CRM

Контракт: fgbfbf 0.2.0, CRM_SPEC 1.1. Адрес API: `http://10.77.77.1:8088`.
Ollama и GPU-worker остаются на отдельном ИИ-сервере. VPN не перенастраивается.

## Деплой

На сервере **CRM** положить готовый приватный файл в `/root/crm-ai-connection.env`.
Он содержит `AI_SERVICE_BASE_URL`, `AI_SERVICE_REPLY_KEY`, `AI_SERVICE_ADMIN_KEY`.
Значения ключей не хранить в репозитории. Файл не нужно присылать в чат.
Штатный `scripts/deploy/vps/compose.sh` подхватывает этот файл вторым `--env-file`;
общий блок окружения передаёт значения в api и worker. Основной `.env` не переписывается.
Другой путь задаётся через `AI_ENV_FILE`. При прямом вызове Compose вне скрипта нужно
самостоятельно передать оба `--env-file`.

```bash
cd /root/crm
git pull --ff-only
chmod 600 /root/crm-ai-connection.env
bash scripts/deploy/vps/update.sh
bash scripts/deploy/vps/check-ai.sh
```

Если файла пока нет, код CRM всё равно разворачивается: админка покажет отсутствие ключей.
Миграция `0121_ai_integration` создаёт состояние чатов, запросы, персональный журнал и
триггеры актуальности сообщений. На существующих чатах ИИ остаётся выключенным.
Флаг `AI_AUTO_REPLIES_ENABLED=false` по умолчанию блокирует генерацию и отправку клиентам.
Включать его только после серверной приёмки, затем включать отдельные тестовые чаты.
Тестовый чат администратора работает независимо от этого флага.

## Администратору

Открыть «Управление ИИ». Сначала проверить подключение и список установленных моделей,
затем сохранить новую версию промпта, проверить её в тестовом чате и отдельно активировать.
Редактирование каталога и промпта не запускает обучение. Изменения настроек сериализованы;
устаревшая форма подключения или каталога получает конфликт вместо перезаписи чужой правки.

В тестовом чате запрос сохраняется в CRM до HTTP-вызова. Закрытие браузера не отменяет
worker; последние запросы восстанавливаются при открытии. С успешного ответа можно создать
или исправить пример; одобрение выполняется отдельно. Экспортируются только одобренные примеры.

Датасет можно загрузить готовым JSONL/GZ, собрать из одобренных примеров или подготовить
из сырой выгрузки CRM. Подготовка проходит в worker CRM, не на ИИ-сервере. Предпросмотр
ограничен 200 вариантами и 8 МБ; входной/распакованный архив — 32 МБ. Большой архив нужно
разделить. Email, ссылки, телефоны и длинные числовые реквизиты заменяются согласованными
метками внутри диалога. ФИО, адреса и смысл ответов проверяются вручную. Вложения не читаются.
Выбранный эталонный ответ не входит в свою историю. Для каждого примера нужно заполнить
системный контекст. Создание датасета не означает одобрение; три подтверждения выставляет администратор.

Перед массовым импортом согласовать срок хранения реальных данных. ИИ-сервис сохраняет
историю запросов; очистка тестового диалога в UI не удаляет её. Временный архив в CRM
очищается из тела задачи после подготовки или ошибки, результат предпросмотра остаётся в БД.

Обучение запускается на явно выбранной исходной модели и одобренном датасете. Сервис
проверяет ресурсы; CRM не подменяет T-Pro на T-Lite и не останавливает другие процессы.
Статусы и события читаются с реального сервиса. После timeout создания задачи сначала
обновить список; не повторять запуск вслепую. Закрытие страницы не останавливает обучение.
Кандидат требует теста, человеческого одобрения и отдельной активации. Откат доступен
через сохранённый `activation_id` в журнале CRM.

## Чаты и доставка

OFF — генерации нет. ASSISTANT — ответы по входящим сообщениям. MANAGER — отвечает
сотрудник; подстраховка включается отдельно. Ответ человека переключает ASSISTANT в MANAGER.
Первое неотвеченное входящее задаёт срок +15 минут; последующие сообщения его не переносят.
Человеческий ответ завершает эпизод. Подстраховка резервируется один раз; неопределённая
доставка требует проверки человеком. Существующий автоответчик вне рабочего времени
не отвечает параллельно с активным режимом ИИ.

Триггеры сообщений/статуса/перевода чата увеличивают ревизию. Worker сохраняет снимок
и request_id до вызова API, проверяет состояние по id перед повторным POST, обрабатывает
202 и terminal-статусы. Межпроцессные advisory locks защищают обработку одного запроса.
Перед подготовкой исходящего сообщения и перед доставкой проверяются ревизия, OFF,
глобальный флаг, закрытие/архив, блокировка контакта и Telegram-ник в чёрном списке.
В outbox уникальны request_id и idempotency_key сообщения. Запись сообщения и outbox атомарна.
Неподтверждённая внешняя доставка автоматически не повторяется; абсолютная exactly-once
гарантия внешнего канала не заявляется. Автоматическая доставка использует существующий
bot-канал CRM и требует внешнего идентификатора контакта.

Handoff сохраняет уведомление, публикует событие закреплённому сотруднику либо группе/отделу;
не создаёт нового владельца. Непрочитанные уведомления доступны при следующем подключении.
Внутренние комментарии и системные сообщения не включаются в контекст; последние 50
текстовых сообщений передаются явно. Превышение бюджета сервиса даёт ошибку и передачу
человеку; автоматического резюмирования нет.

## Маршруты CRM

- `/api/v1/ai/status`, `/journal`, `/requests`, `/requests/{id}`, `/preparations` — admin.
- `/api/v1/ai/service/{path}` — белый список административных операций контракта;
  браузер никогда не обращается непосредственно к ИИ API.
- `/api/v1/ai/prepare-export` — постановка сырого архива в локальную очередь, admin.
- `/api/v1/ai/chats/{id}` GET/PUT — права обработки и область видимости чата.
- `/api/v1/ai/notices` — уведомления только по доступным чатам.

401 внешнего сервиса преобразуется в ошибку интеграции 502, а не выход пользователя из CRM.
Ключи — SecretStr в серверных настройках, GET показывает только факт наличия.

## Серверная приёмка — обязательна до автоответов

Локальные запуски приложения и runtime-тесты не выполнялись согласно ТЗ. Статические
проверки не подтверждают работоспособность сети, GPU или доставки.

1. `check-ai.sh`: авторизованные capabilities и connection из api и worker.
2. Проверить запрет admin API для других ролей и переключения чужого чата.
3. Создать/протестировать/активировать промпт. Проверить 200, 202, timeout и восстановление
   того же request_id после перезапуска worker/вкладки.
4. В тестовом канале проверить новое входящее, ответ человека, OFF, закрытие и передачу
   во время генерации; старый результат не должен отправляться.
5. Проверить 15 минут с несколькими входящими, один fallback, два worker и сбой доставки.
6. Проверить повреждённый GZ, предпросмотр, обезличивание и отдельное одобрение.
7. На подходящей GPU выполнить реальное обучение → метрики → тест кандидата → одобрение →
   активация → откат. Проверить insufficient_resources, отмену и restart worker.

Полный цикл генерации/обучения и конкурентной доставки на сервере этой версией ещё не подтверждён.
