# Глобальная блокировка Telegram-контакта

В заголовке диалога доступна кнопка «Заблокировать» для сотрудников с правом
`chats.write` и доступом к самому диалогу. В CRM нет кнопки или API разблокировки.
Перед отправкой требуется подтверждение; причина необязательна (до 500 символов).

Команда `block_contact` отправляется обычной подписанной очередью на outbound_url
бота диалога. Telegram ID берётся из контакта на сервере, а автор — из авторизации.
Блокировка действует на Telegram ID во всех ботах, а не только на открытый диалог.

Состояния: нет запроса, ожидает, подтверждено, не подтверждено. HTTP 200 сам по себе
не означает успех: требуется `status=ok`, `is_access=false` и совпадающий числовой
`telegram_user_id`. Повторные нажатия при ожидании/успехе не создают новую команду.
Сетевые ошибки повторяются существующей очередью с тем же request_id; постоянные
4xx (кроме 429) и некорректные подтверждения завершаются ошибкой.

Запрос и подтверждение записываются в аудит contact.update с типами
`telegram.block.requested` / `telegram.block.confirmed`. Подробности доставки
сохраняются в bot_outbound_log. Секреты в аудит не передаются.
Подтверждённая блокировка запрещает отправку через CRM и её очередь.
Ответ моста `error_code=contact_blocked` не считается доставкой и не повторяется.

## Развёртывание

Обновить API, worker и frontend обычным update.sh. Новых миграций нет.
На стороне app-crm-bridge предварительно должна быть реализована команда
block_contact и ответ по спецификации. Все Telegram-боты должны проверять
bot_users.is_access на входящих; рассылки также должны учитывать этот флаг.
CRM не может проверить раскатку middleware на всех ботах по одному ответу моста.
Состояние в CRM — последнее подтверждение моста, не обратная синхронизация БД.

Проверка после раскатки: на тестовом контакте подтвердить блокировку, дождаться
статуса, проверить отсутствие входящих в два бота и исключение из рассылки.
Реальным клиентам команды в ходе локальных тестов не отправляются.
