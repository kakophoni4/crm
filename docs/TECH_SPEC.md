# Техническое задание (TECH SPEC)

> Документ описывает **что** должна делать система. **Как** реализовано — в `ARCHITECTURE.md`, `DATABASE.md`, `API_CONTRACT.md`.

---

## 1. Бизнес-цель

Построить внутренний CRM-инструмент для команды, которая ведёт клиентскую работу через Telegram. Главный экран — чат-центр: оператор видит свои чаты, переписывается, заполняет карточку клиента. Над операторами — старшие, над всеми — админ. Несколько Telegram-ботов, каждый закреплён за отделом или группой.

Главные качества системы (в порядке приоритета):
1. Корректность прав доступа (никто не видит лишнего).
2. Удобство и скорость работы оператора (UX чата, минимум кликов).
3. Аудит и прозрачность («кто что делал»).
4. Готовность к росту: ещё каналы (WhatsApp, VK), больше ботов и операторов.

## 2. Глоссарий

| Термин | Описание |
|---|---|
| **User (Оператор)** | Рядовой сотрудник, ведёт чаты, видит только своё. |
| **Senior (Старший юзер)** | Руководитель отдела, управляет чатами и юзерами своего отдела. |
| **Admin** | Полный доступ ко всему. Создаёт отделы и старших. |
| **Department (Отдел)** | Верхняя организационная единица. У отдела один Senior. |
| **Group (Группа)** | Подразделение внутри отдела. Юзер принадлежит ровно одной группе. |
| **Contact (Контакт)** | Глобальная карточка клиента (поля, Telegram). **Владение** — отдельно **в каждой группе** → [`CONTACT_OWNERSHIP.md`](CONTACT_OWNERSHIP.md). |
| **Contact ownership (Владение карточкой)** | Запись `(contact_id, group_id) → owner_user_id`. Передаётся **внутри группы**; не затрагивает другие группы/боты того же клиента. |
| **Chat (Чат)** | Тред переписки `(contact_id, bot_id)`. **Общий для группы**: любой user группы может читать/писать; приоритет уведомлений у **владельца карточки**. |
| **Bot** | **Внешний сервис** (готовый бот, разработан отдельной командой), который общается с клиентом в Telegram. Закреплён за **группой** (или отделом). CRM ↔ Bot — HTTP+HMAC ([`BOTS_INTEGRATION.md`](BOTS_INTEGRATION.md)). |
| **Takeover (Перехват)** | Старший временно подключается к чату; оператор не может писать (отдельно от «ответа за коллегу» — см. on_behalf в ownership). |
| **Transfer (Передача)** | **Карточка контакта** в рамках **одной группы** переходит другому оператору (не передача «чата»). |
| **Escalation (Эскалация)** | Если владелец не ответил за **N минут** (настраивает senior) → уведомление всей группе; для нового клиента — перераспределение владельца. |
| **Status** | Справочник `statuses` с полем `kind`: **`chat_label`** (метка чата: новый/постоянный клиент) или **`lead_pipeline`** (воронка сделки). См. [`LEADS.md`](LEADS.md). |
| **Lead (Лид)** | Одна сделка / цикл работы с клиентом в **группе** `(contact_id, group_id)`. Воронка на `leads.status_id`; закрытие — `closed_at`. Повторное inbound после закрытия → **новый** лид. Канон: [`LEADS.md`](LEADS.md). |
| **crm_summary** | API-агрегат счётчиков открытых лидов и распределения по этапам воронки в scope актора **без** детализации чужих лидов. См. [`API_CONTRACT.md`](API_CONTRACT.md) §9. |

## 3. Роли и иерархия

```
Admin (1..n)
 └─ создаёт ─▶ Department (с Senior'ом во главе)
                  │
                  └─ Senior владеет/управляет ─▶ Department.groups[]
                                                        │
                                                        └─ Senior создаёт ─▶ Group
                                                                              │
                                                                              └─ Senior создаёт ─▶ User (в свой отдел)
```

### Правила

- **User** принадлежит ровно **одной группе**, через неё привязан к отделу.
- **Senior** — это `User` с особой ролью, привязанный к отделу как `head_user_id`.
- **Admin** не привязан ни к группе, ни к отделу.
- Senior создаёт юзеров **только** в свой отдел.
- Senior создаёт группы **только** в свой отдел.
- Senior **не может** изменить чужой отдел.
- Admin может перенести юзера/группу между отделами.

## 4. Видимость данных (Scope)

> Подробная матрица — в `RBAC_MATRIX.md`. Здесь — суть.

### 4.1 Видимость пользователей

- **User**: видит только участников своей группы и Senior'а своего отдела. Никого больше.
- **Senior**: видит весь свой отдел. Юзеров других отделов — нет.
- **Admin**: видит всех.

### 4.2 Видимость чатов

> Канон: [`CONTACT_OWNERSHIP.md`](CONTACT_OWNERSHIP.md).

- **User**: все чаты **своей группы** (боты с `owner_type=group` и `owner_id = group_id` пользователя). В списке: фильтры «Мои карточки» (я владелец) / «Вся группа» / «Нужен ответ» (эскалация).
- **Senior**: все чаты отдела.
- **Admin**: все чаты.
- **Писать** в чат группы может **любой** user этой группы; в UI и аудите фиксируется **владелец карточки** и **фактический автор** ответа.

### 4.3 Видимость контактов

- Контакт виден, если есть хотя бы один чат в видимой группе/отделе.
- **Владение** задаётся per-group: `contact_group_assignments`. Один клиент в bot₁ (группа A) и bot₂ (группа B) → **два владельца** (по одному в каждой группе).
- Передача в другую группу **не через transfer API** — добавление user в группу (оргструктура).
- Telegram username — при доступе к контакту; **telegram_user_id** — только admin.

## 5. Сценарии (User Stories)

### 5.1 Аутентификация
- Логин по email + пароль → access (15 мин) + refresh (30 дней).
- Refresh-токен хранится в Redis, может быть отозван.
- Logout → отзыв refresh.
- Принудительный logout пользователя (админом) → отзыв всех refresh.

### 5.2 Создание оргструктуры
- **US-1.** Admin создаёт отдел, указывает имя.
- **US-2.** Admin назначает Senior отдела (выбирает из существующих юзеров или создаёт нового).
- **US-3.** Senior создаёт группу в своём отделе.
- **US-4.** Senior создаёт юзера в своём отделе, выбирает группу.
- **US-5.** Senior отключает юзера (soft delete), его чаты возвращаются в пул отдела.

### 5.3 Чат-центр
- **US-10.** Оператор открывает раздел «Мои чаты», видит список своих активных чатов с контактами, последним сообщением, статусом, индикатором непрочитанных.
- **US-11.** Оператор пишет в чат — сообщение уходит в Telegram через привязанного бота.
- **US-12.** Контакт пишет в Telegram — сообщение прилетает оператору в realtime, бейдж непрочитанных растёт.
- **US-13.** Оператор меняет статус чата.
- **US-14.** Оператор заполняет карточку контакта — каждая правка фиксируется в истории «кто и когда».
- **US-15.** Оператор инициирует **передачу карточки контакта** (в своей группе) другому оператору группы → запрос Senior'у (если инициатор user).
- **US-16.** Любой оператор группы может ответить в чате «чужой» карточки; в истории видно: **владелец карточки**, **кто ответил**, **когда**.
- **US-17.** Senior задаёт **N минут** ожидания ответа владельца; при превышении — уведомление всей группе.
- **US-18.** Для **нового** клиента в группе: если владелец не ответил за N — перераспределение на **первого ответившего** или **случайного available** (стратегия на группу).

### 5.4 Передача карточки контакта (transfer) — внутри группы

```
[1] User A: "передать карточку контакта X (группа G) → User B"
       │
       ▼
[2] Senior получает запрос на апрув (если инициатор user):
       ├─ Approve  ─▶ [3]
       └─ Reject   ─▶ владелец остаётся A
       │
       ▼
[3] User B: [Принять] [Отклонить]
       ├─ Accept   ─▶ contact_group_assignments(owner)=B для (X, G)
       └─ Decline  ─▶ владелец остаётся A
```

Особенности:
- Меняется **только** владение `(contact, group_id)`. Чаты того же контакта в **других группах/ботах** не затрагиваются.
- **Senior** передаёт внутри отдела; **admin** — `force=true` с аудитом.
- Межгрупповая работа — **добавить user в группу**, не transfer API.

### 5.5 Перехват (takeover)
- **US-20.** Senior открывает чужой чат своего отдела → нажимает «Подключиться».
- При активном takeover:
  - У оператора чат переходит в режим «только чтение», input заблокирован, баннер «Сейчас в чате руководитель: <имя>».
  - Senior пишет от своего имени, в сообщении в БД `author_user_id = senior.id`.
  - В Telegram сообщение уходит так же, как и от оператора (контакт не различает).
- **US-21.** Senior нажимает «Отключиться» → input разблокируется у оператора, баннер исчезает.
- Только один активный takeover на чат.

### 5.6 Боты (multi-bot integration)
- **US-30.** Admin регистрирует нового бота в CRM: вводит `code`, `name`, `purpose`, выбирает владельца (отдел или группа), указывает `outbound_url` бота.
- Система генерирует пару HMAC-секретов (`inbound_secret` для верификации входящих от бота, `outbound_secret` для подписи команд CRM → бот). Секреты возвращаются **один раз** в ответе UI.
- Разработчик бота прописывает эти секреты у себя и реализует контракт по [`BOTS_INTEGRATION.md`](BOTS_INTEGRATION.md).
- **US-31.** Бот шлёт `message.received` → CRM создаёт/находит контакт и чат `(bot, contact)`. Определяется **group_id** бота. Если нет `contact_group_assignments(contact, group)` — **назначается владелец карточки** (round-robin among available). Уведомление **сначала владельцу**; таймер N минут.
- **US-32.** Один контакт в **разных ботах/группах** → разные чаты, **разные владельцы карточки per group**, одна глобальная карточка полей.
- **US-33.** Admin может ротировать секреты бота (`POST /bots/{id}/rotate-secret`). При смене `inbound_secret` действует grace-period 5 минут (старый ключ принимается).
- **US-34.** Если `outbound_url` бота недоступен > N минут — health-check помечает бота как «не отвечает», в UI отображается плашка, отправка ставится в очередь до восстановления.

### 5.7 Поиск
- Поиск по имени контакта, телефону, telegram username.
- Поиск по тексту сообщений в видимых чатах.
- Старт — Postgres FTS, потом Meilisearch.

### 5.8 Уведомления
- **Приоритет 1:** владелец карточки в группе (новое входящее).
- **Приоритет 2:** через N минут без ответа владельца — вся группа (эскалация).
- Realtime: transfer карточки, takeover, `contact.ownership.reassigned`.
- Десктоп / push — опционально.

## 6. Нефункциональные требования

| Категория | Требование |
|---|---|
| Производительность | Доставка входящего сообщения в UI оператора ≤ 1 сек p95. |
| Масштаб (старт) | До 100 операторов одновременно онлайн, до 50 ботов, до 5k активных контактов. |
| Доступность | Целевое — 99% (внутренний инструмент, не публичный). |
| Безопасность | TLS 1.2+, bcrypt/argon2 для паролей, refresh-tokens с отзывом, secrets в Vault/env. |
| Логирование | Структурный JSON-лог, корреляция request_id, маскирование PII. |
| Аудит | Все изменения сущностей оргструктуры, контактов и чатов — в `audit_log`. |
| Бэкап | Postgres — daily, retention 14 дней. MinIO — daily, retention 14 дней. |
| Локализация | Только русский язык для UI на старте. |
| Браузеры | Последние 2 версии Chrome/Edge/Firefox, Safari 16+. |

## 7. Out of scope (на старте)

- WhatsApp, VK, Instagram — только Telegram.
- Голосовые звонки.
- Биллинг и платежи.
- Публичная регистрация (только админ создаёт пользователей).
- Мобильные нативные приложения (только адаптивный веб).
- Многоязычность.
- Шифрование сообщений end-to-end (для внутреннего CRM избыточно).

## 8. Слабые места ТЗ (риски)

1. **Лимит 30 msg/sec на бота в Telegram** — это ответственность авторов ботов. Если бот не реализовал rate-limit/queue, при массовых отправках от CRM мы получим много `error_code: rate_limited`. Зафиксировать в `BOTS_INTEGRATION.md` как требование к ботам.
2. **«Один контакт = одна карточка для разных ботов/отделов»** — тонкая зона приватности: отдел A может увидеть в карточке, что контакт также общается с отделом B (через вкладку чатов). Нужно явное правило: показываем существование чата в другом отделе или нет.
3. **Takeover и Telegram** — клиент не видит, что писал не оператор, а старший. Это сознательное решение, но юридически в некоторых отраслях это претензия. Зафиксировать в политике.
4. **Передача карточки с double-confirm** — нужны звуковые уведомления для принимающего.
9. **Ответ «за коллегу»** — обязателен аудит; без `message_reply_audit` нельзя разбирать споры.
10. **Гонка first_responder** — два оператора ответили одновременно; нужна транзакция на смену владельца.
5. **Маскирование telegram_user_id маскированием в API** не равно шифрованию в БД. Если БД утечёт — ID утечёт. Если регулятор требует, нужно `pgcrypto` + ключ в Vault.
6. **Доверие к ботам.** Контракт требует от ботов идемпотентности по `request_id`. Если бот не реализовал — повторный запрос отправит дубль клиенту. CRM не может это проверить, только мониторить через метрики и претензии. Включить в test-bot обязательную проверку.
7. **Утечка `inbound_secret` бота** = атакующий может вбрасывать фейковые входящие. Митигация: ротация при подозрении, IP allowlist, мониторинг частоты `signature_failures`.
8. **Зависимость от готовых ботов** — если другая команда не успевает, чат-центр не запустить. Решение: писать тесты с mock-ботом (отдельный сервис, реализующий тот же контракт), запускать против него весь функционал.
