# QA

> Качество, автоматизация тестов, нагрузочное тестирование, регрессы, security pass.

---

## 1. Зона ответственности

- Тест-стратегия и тест-план для каждой фазы.
- Автоматизация:
  - юнит-тесты (с Backend-командами);
  - интеграционные API-тесты (FastAPI + httpx + testcontainers);
  - **матрица RBAC**: автоматический прогон «роль × эндпоинт × действие» против ожиданий из `RBAC_MATRIX.md`;
  - E2E-сценарии (Playwright) на критичные пути;
  - нагрузочное (k6) — RPS API, WS-коннекты, поток bot-events;
  - chaos-light: падение Redis/Postgres → как ведёт себя приложение.
- Регрессионный пакет.
- Bug triage и приоритизация.
- Security pass перед релизом.

## 6. Слабые места

1. **E2E через настоящих ботов** — flaky (зависимость от внешней команды и Telegram). Митигация: тестовые сценарии используют **mock-бота** (отдельный сервис, реализующий контракт `BOTS_INTEGRATION.md`: принимает `send_message`, отвечает ok/error, может пушить `message.received`). Реальные боты — только smoke-тест после деплоя.
2. **Парсер `RBAC_MATRIX.md`** хрупок к изменениям формата. Альтернатива: вести правила в `rbac.yaml` рядом, а .md генерировать из него.
3. **Нагрузочные тесты без отдельного стенда** ломают staging. Поднять отдельный perf-env.
4. **Security pass раз в релиз** недостаточно при активной разработке. Включать `bandit` и `trivy` в CI.
5. **Visual regression** дорогой и flaky — на старте без него; добавить, когда UI стабилизируется.
6. **Chaos-тесты в CI** долгие. Прогонять только nightly, не на каждом PR.
