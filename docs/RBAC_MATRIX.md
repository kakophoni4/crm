> Этот файл — **источник истины** для проверок доступа. Любое изменение здесь = изменение в `core/auth/permissions.py`, `rbac.py`, `scope.py`. Не наоборот.

## 1. Роли

| Код | Название | Кто такой |
|---|---|---|
| `user` | Оператор | Рядовой сотрудник, ведёт чаты внутри своей группы |
| `group_senior` | Старший группы | Права старшего в рамках своих групп; может принудительно менять владельца карточки |
| `senior` | Старший | Руководит отделом, управляет юзерами и чатами своего отдела |
| `admin` | Администратор | Глобальные права, создаёт оргструктуру |
| `accountant` | Бухгалтер | Кабинет бухгалтерии и задачи |
| `chief_accountant` | Главный бухгалтер | Бухгалтерия + управление задачами |
| `lawyer` | Юрист | Кабинет: задачи, тикеты ЕГРЮЛ, парсер лавок, телефония |

## 2. Скоупы видимости

Каждый запрос к данным определяет **scope** — границу видимости актора.

| Scope | Кто получает | Применение |
|---|---|---|
| `OWN` | сам объект, привязанный к актору (например, его собственный chat) | оператор |
| `GROUP` | объекты группы актора | оператор (для users) |
| `DEPARTMENT` | объекты отдела актора | senior |
| `ALL` | все | admin |

Сводная таблица «scope для роли по сущности»:

| Сущность \ Роль | user | senior | admin |
|---|---|---|---|
| **users (видимость)** | GROUP + senior отдела | DEPARTMENT | ALL |
| **groups (видимость)** | OWN (своя группа) | DEPARTMENT | ALL |
| **departments (видимость)** | свой отдел (имя/список групп, без юзеров чужих групп) | свой отдел | ALL |
| **chats (видимость)** | GROUP (все чаты ботов своей группы) | DEPARTMENT | ALL |
| **messages (видимость)** | равно chats | равно chats | ALL |
| **contacts (видимость)** | контакты с чатом в своей группе | контакты отдела | ALL |
| **contact ownership** | видит owner per group; я владелец = «мои карточки» | настройка N, transfer в отделе | ALL |
| **bots (видимость)** | боты своей группы/отдела (только username, purpose) | то же | ALL (включая token, статистика) |
| **statuses (справочник)** | ALL (read) | ALL (read) | ALL |
| **audit_log** | OWN (только свои действия) | DEPARTMENT (действия в своём отделе) | ALL |
| **contact_field_changes** | по правилу видимости контакта | то же | ALL |

## 4. Постоянные нюансы

### 4.1 Видимость самого себя
Любая роль видит свой профиль и свои действия в логах.

### 4.2 Senior как user
Senior — это user отдела с дополнительной ролью. Он видит юзеров своего отдела (включая себя), и сам в списке появляется как senior.

### 4.3 Видимость user'а в группе
User видит:
- всех других user'ов своей группы (без личных контактов, только профиль),
- senior'а своего отдела (как контакт-руководителя),
- НЕ видит user'ов других групп своего отдела.

### 4.4 Удаление senior'а
Если senior удаляется, отдел остаётся «без головы» до назначения нового. В этот период:
- юзеры отдела видят только себя и других юзеров своих групп,
- никто из них не может апрувить transfer'ы — задачи висят, пока админ не назначит senior'а.

### 4.5 Множественные группы / отделы
**На старте — нет.** User в одной группе, senior — head ровно одного отдела. Если бизнес попросит «senior двух отделов» — это потребует пересмотра schema (`user_department_roles` many-to-many) и переписывания scope-функций.

## 5. Реализация в коде

### 5.1 Реестр permission'ов
```python
# core/auth/permissions.py
class P:
    USERS_READ = "users.read"
    USERS_CREATE = "users.create"
    # ... и т.д.
    CONTACTS_READ_TG_ID = "contacts.read_tg_id"
    CHATS_TAKEOVER = "chats.takeover"
    CHATS_TRANSFER_FORCE = "chats.transfer.force"
    BOTS_MANAGE = "bots.manage"            # CRUD ботов, ротация секретов
    BOTS_DEACTIVATE_DEPT = "bots.deactivate.dept"  # senior может выключать ботов своего отдела
```

### 5.2 Маппинг ролей
```python
ROLE_PERMISSIONS = {
    "user":   {P.CHATS_READ, P.CHATS_WRITE_OWN, ...},
    "senior": {P.CHATS_READ, P.CHATS_WRITE_OWN, P.CHATS_TAKEOVER, P.USERS_CREATE_DEPT, ...},
    "admin":  set(P.__dict__.values()),  # все
}
```

### 5.3 Scope-резолвер
```python
def build_chat_scope(actor: User) -> ChatScope:
    if actor.role == "admin":
        return ChatScope.ALL
    if actor.role == "senior":
        return ChatScope(department_ids=[actor.head_department_id])
    return ChatScope(user_ids=[actor.id])
```

Каждый репозиторий в SELECT добавляет `WHERE` из scope.

### 5.4 Защита от обхода в API
- Доменный объект (например, `Chat`) **никогда** не возвращается из репозитория без применённого scope.
- Тесты RBAC обязательны: матрица ролей × действий, проверка через httpx-клиент.

### 5.5 Глобальный поиск (`GET /api/v1/search`)
- Контакты: `visible_user_ids` (как `GET /contacts`).
- Сообщения и чаты: `CHATS_READ_*` + `chat_visibility_clause` (FTS — как `GET /chats/search`).
- **Rate-limit:** 60 запросов/мин на `user_id` (`rate_limited` / HTTP 429); см. §6.4.

## 6. Слабые места матрицы

1. **«Senior отдела без замены» — слепая зона.** Пока админ не назначит нового, апрувы transfer'ов висят. Решение: эскалация админу через 24 часа.
2. **Force-transfer админом без согласия** — потенциал жалоб от юзеров. Решение: явный аудит-флаг + email-уведомление принимающему.
3. **`contacts.read_tg_id` только админ** — но если админу нужен помощник (читать tg_id), потребуется новая роль `compliance` или гибкий permission. Зафиксировать как «когда понадобится — добавим роль, не расширяя admin».
4. **Поиск контакта по `telegram_username`** может через брутфорс деанонимизировать наличие контакта в системе. Митигация: rate-limit на поиск + только в видимом scope.
5. **Чат в пуле (current_user_id IS NULL)** — `OWN`-scope не покрывает. Юзер не видит. Это сознательно, но senior должен явно мониторить пул.
